# Requirements Document

## Introduction

This feature implements the assessment-first Clinical Decision Support (CDS) gate required by ADR-20260703-01. The feature separates an editable Assessment from a physician-confirmed Assessment, applies deterministic red-flag routing before candidate display and before protected generation, provides a bounded non-treatment CPG Preview for diagnosis candidates, and enforces both the gate and server-owned per-diagnosis generation eligibility for every protected output. The feature also defines contract-first API sequencing, ADR-aligned CDS persistence and DynamoDB access patterns, safety-focused test coverage, and documentation updates. A complete OpenAPI contract with passing contract validation and documented/locked implementation defaults is the readiness boundary for downstream implementation; this specification does not define a runtime implementation-work state machine.

The broader Clinical Knowledge Operations source-registry lifecycle, ingestion/review/publication tooling, vector retrieval, and bulk diagnosis-card onboarding remain outside this feature. This feature consumes only immutable, already-approved catalog and source metadata selected by the active policy bundle.

## Glossary

- **Assessment_Gating_System**: The complete assessment-first CDS capability governed by ADR-20260703-01.
- **Physician**: An authenticated user in the `doctor` Cognito group who is assigned to the Consultation.
- **Consultation**: A doctor-patient clinical encounter identified by `consultationId` in the JSON API contract.
- **Post_Consult_State**: A Consultation whose canonical consultation-scoped Session projection has authoritative status `ended`; booking status or a permissive legacy session view cannot establish this state.
- **Editable_Assessment**: An unconfirmed diagnosis value selected or manually entered by the assigned Physician; an Editable_Assessment cannot unlock protected generation.
- **Editable_Assessment_Revision**: A monotonically increasing concurrency fence changed by every candidate selection, manual edit, clear, or other Editable_Assessment replacement; confirmation binds the exact revision and digest reviewed by the Physician.
- **Confirmed_Assessment**: A non-empty diagnosis explicitly confirmed by the assigned Physician as the Physician's clinical judgment.
- **Assessment_Version**: The current non-negative integer for Assessment state transitions; version 0 denotes that no Assessment has ever been confirmed, and each successful confirmation, update, or clear transition increases the current version by exactly 1.
- **Clinical_Input_Revision**: A monotonically increasing identifier allocated by the authoritative Clinical_Input_Head when the canonical source vector, source-membership version, canonicalization version, or normalized digest changes.
- **Clinical_Input_Source_Fence**: A monotonically increasing value advanced atomically by every authoritative clinical-input source mutation; tokens, jobs, and artifacts bind it so a source change is immediately detectable before normalization catches up.
- **Clinical_Input_Head**: The consultation-scoped, strongly consistent authority for source membership, source revisions, Clinical_Input_Source_Fence, Clinical_Input_Revision, canonicalization version, normalized digest, and normalization-complete fence.
- **Clinical_Input_Snapshot**: An immutable, bounded record of the authoritative source entity keys, source revisions, source-membership version, Clinical_Input_Source_Fence, canonicalization version, normalized-input digest, and Clinical_Input_Revision used for one candidate, routing, token, or generation decision.
- **Gate_Revision**: A monotonically increasing concurrency fence for authoritative gate, lock, acknowledgment, token-family, and safety-transition state.
- **Policy_Activation_Revision**: A monotonically increasing environment-scoped activation revision selecting one immutable compatible bundle of ruleset, diagnosis catalog, prompt, template, output-schema, grounding, and model-profile versions.
- **Candidate_Evaluation**: An immutable result of an idempotent candidate-stage safety evaluation, bound to input, ruleset, catalog, and evaluation versions; side-effect-free search and scrolling operate within this snapshot.
- **Catalog_Version**: The immutable identifier of the diagnosis-name catalog and deterministic ordering rules used for one Candidate_Evaluation.
- **CPG_Preview**: A side-effect-free, candidate-scoped pre-confirmation view containing bounded structured support facts, confirmation questions, and one approved source reference; it is separate from the diagnosis-name-only candidate item and cannot contain treatment or Protected_Output content.
- **Generation_Eligibility**: Immutable server-owned catalog metadata consisting of capability `full_solver`, `reference_only`, or `unmapped_manual`, an allowed Protected_Output-type set, and a canonical digest. A `reference_only` or unmatched manual Assessment has an empty allowed set until a new reviewed catalog version is activated.
- **Effective_Staleness**: The authoritative stale classification computed from stored stale state and current Assessment, clinical-input source-fence, assignment, invalidation-watermark, and token-family-epoch state rather than requiring every artifact item to be synchronously updated.
- **Token_Family_Epoch**: A monotonically increasing authorization epoch within one Assessment_Version; revocation permanently closes one epoch, and successful governed recovery creates a new epoch rather than unrevoking history.
- **Assessment_Service**: The server-side component that edits, confirms, updates, clears, versions, and retrieves Assessment state.
- **Diagnosis_Candidate**: A diagnosis-name item offered to the Physician for selection without a confidence score, solver name, rank value, code, or AI attribution.
- **Candidate_Service**: The server-side component that derives and returns Diagnosis_Candidates.
- **Red_Flag_Router**: The deterministic server-side component that evaluates Normalized_Clinical_Input and produces a Red_Flag_Outcome with rule identifiers.
- **Red_Flag_Outcome**: One of `ROUTINE`, `WARNING`, `REFER_F2F`, `EMERGENCY`, or `EVALUATION_FAILED`; only `ROUTINE` permits Protected_Output generation.
- **Gate_Token**: A signed, expiring credential bound to `consultationId`, `assessmentVersion`, `tokenFamilyEpoch`, `physicianActorId`, Clinical_Input_Revision, Clinical_Input_Source_Fence, Gate_Revision, and a unique token identifier.
- **Continuation_Grant**: A non-exportable server-side authorization attached to one admitted async job, minted only from a valid Gate_Token, bounded by a configured job deadline, and insufficient without complete start/resume/completion revalidation.
- **Idempotency_Reservation**: The durable actor/operation/Consultation-scoped state machine that serializes a write intent before side effects and records lease ownership, provider-invocation certainty, terminal response, recovery status, and replay data.
- **Gate_Token_Service**: The server-side component that issues, verifies, expires, and revokes Gate_Tokens.
- **Protected_Generation_Service**: The server-side component that creates Protected_Outputs after all gate checks pass.
- **Protected_Output**: One of seven protected output types: Plan, prescription, final ICD code, medical certificate, lab request, imaging request, or patient education artifact.
- **Dependent_Artifact**: A Protected_Output or protected CDS draft linked to a specific Assessment_Version.
- **Stale_Artifact**: A Dependent_Artifact that cannot be finalized, released, or treated as current because the linked Assessment_Version or gate state is no longer current.
- **Current_Output_View**: An authorized response or selection that contains only non-stale Dependent_Artifacts linked to the current Assessment_Version.
- **History_View**: An authorized audit or clinical-history response that may contain current and stale Dependent_Artifacts with explicit stale status and linked Assessment_Version.
- **CDS_Data_Store**: The ADR-aligned persistence layer in the `app_core` DynamoDB single-table design for Assessment state, gate revocation state, red-flag results, candidates, drafts, and artifact dependencies.
- **Normalized_Clinical_Input**: The schema-validated, normalized clinical facts evaluated by deterministic candidate and red-flag rules.
- **Ruleset_Version**: The immutable identifier for deterministic rule definitions used in one red-flag or candidate evaluation.
- **Implementation_Readiness_Authority**: The validated contract, documented technical baseline, and reproducible repository evidence that permit implementation to continue without a named-person approval transition.
- **Idempotency_Key**: A client-generated UUID that identifies one write intent.
- **Idempotent_Replay**: A repeated write with the same Idempotency_Key and payload that returns the original response without repeating state changes, generation, fallback, or audit events that represent a new operation.
- **ICD**: The International Classification of Diseases coding system used for the final diagnosis code.
- **PHI**: Protected health information that can identify a patient or expose patient clinical data.
- **OpenAPI_Contract**: The OpenAPI 3.1 source of truth at `contracts/openapi.yaml`.
- **API_Gateway**: The server-side HTTP API boundary that authenticates callers and routes requests to Lambda handlers.
- **AI_Inference_Service**: The existing Together.ai-backed CDS inference capability and deterministic template fallback.
- **Safety_Test_Suite**: The automated unit, property, contract, and integration tests for assessment gating and red-flag behavior.
- **Synthetic_Fixture**: One of the 40 cases in `architecture/bayanhealth_prd_v3_synthetic_intake_test_cases.csv`.
- **Documentation_Set**: The OpenAPI contract, AI inference binding, API documentation, data model, consultation workflow documentation, and session handoff affected by this feature.

## Requirements

### Requirement 1: OpenAPI-First Contract Sequencing

**User Story:** As a platform engineer, I want the assessment gate defined in the API contract before implementation, so that frontend and backend behavior share one reviewed safety contract.

#### Acceptance Criteria

1. THE OpenAPI_Contract SHALL define request and response schemas for Assessment reads, manual Editable_Assessment updates, candidate selection against a committed evaluation, confirmation from any unconfirmed version, Confirmed_Assessment update and clear, idempotent Candidate_Evaluation creation, side-effect-free candidate snapshot search/scroll and candidate-scoped CPG_Preview reads, Gate_Token issuance, red-flag acknowledgment, Current_Output_View, paginated History_View, async job status and cancellation, finalization, release, and seven explicit Protected_Output generation operations; legacy client-driven continuation SHALL be rejected.
2. THE OpenAPI_Contract SHALL require `consultationId`, `assessmentVersion`, `physicianActorId`, and `gateToken` for every Protected_Output generation operation, SHALL use camel case consistently with repository JSON conventions, and SHALL require the path Consultation to match `consultationId` and the authenticated Cognito `sub` to match `physicianActorId`.
3. THE OpenAPI_Contract SHALL document authenticated role, assignment and history scope, idempotency, correlation, cache-control, pagination, expected revisions, success/error envelopes, `202` async behavior, finalization/release policy, and legacy-route behavior for every applicable operation.
4. THE OpenAPI_Contract SHALL define fixed HTTP statuses and machine-readable errors for authentication, assignment concealment, lifecycle, missing Confirmed_Assessment, stale Assessment/Input/Gate revisions, invalid/expired/revoked/mismatched Gate_Token, generation lock, blocked or failed Red_Flag_Outcome, unavailable or stale CPG_Preview, Assessment or output-type generation ineligibility, acknowledgment, stale artifact, idempotency conflict, rate limit, state conflict, and safe internal failure.
5. WHILE the assessment-gating OpenAPI operation/schema/error inventory is incomplete or the repository contract validation check is failing, THE affected boundary behavior SHALL remain incomplete and fail closed; unrelated scaffolding, implementation, tests, and documentation MAY continue.
6. WHEN the complete inventory passes the repository contract validation check, THE OpenAPI_Contract SHALL become the source of truth for backend, frontend, infrastructure routing, tests, and operational documentation without a separate approval transition.
7. THE OpenAPI_Contract SHALL reject protected fields on deprecated legacy routes and SHALL NOT leave SOAP, patient-card, draft-review, post-consult automation, or async continuation as alternate ungated generation paths.

### Requirement 2: Assessment Editing, Confirmation, and Versioning

**User Story:** As a Physician, I want to edit and explicitly confirm my Assessment after the consultation, so that protected clinical generation is based on my recorded judgment.

#### Acceptance Criteria

1. WHEN the canonical Session-ending transaction first sets the consultation-scoped Session projection to `ended`, THE Assessment_Service SHALL conditionally initialize a blank Editable_Assessment, Editable_Assessment_Revision 0, Assessment_Version 0, Clinical_Input_Head, and gate state exactly once in the same bounded transaction; a backward-compatibility lazy initializer MAY perform the same conditional initialization only after a strongly consistent canonical `ended` read.
2. THE Assessment_Service SHALL derive Post_Consult_State only from the strongly consistent canonical consultation-scoped Session projection with status `ended`; booking status, GSI results, duplicated legacy session records, and permissive `completed` strings SHALL be ineligible for Assessment confirmation, update, or clearing.
3. WHEN the assigned Physician selects a Diagnosis_Candidate or manually enters a diagnosis while the Assessment is unconfirmed, THE Assessment_Service SHALL replace the Editable_Assessment, record its source and source evaluation when applicable, increase Editable_Assessment_Revision by exactly 1, and leave Assessment_Version unchanged without creating a Confirmed_Assessment.
4. IF the assigned Physician attempts to edit Editable_Assessment while a Confirmed_Assessment exists, THEN THE Assessment_Service SHALL reject the edit with a state-conflict error and require the explicit Confirmed_Assessment update operation.
5. WHEN the assigned Physician confirms a non-empty Editable_Assessment from any unconfirmed state and supplies the current expected Assessment_Version, Editable_Assessment_Revision, and canonical editable digest, THE Assessment_Service SHALL conditionally confirm exactly that reviewed value and increase Assessment_Version by exactly 1; any intervening edit SHALL return a stale-editable conflict.
6. WHEN the Assessment_Service creates a Confirmed_Assessment, THE Assessment_Service SHALL record the diagnosis text, Physician identifier, confirmation timestamp, source type of `candidate_selection` or `manual_entry`, source Candidate_Evaluation identifier when applicable, confirmed Editable_Assessment_Revision and digest, and resulting Assessment_Version.
7. WHEN the currently assigned Physician successfully updates or explicitly re-attests a Confirmed_Assessment, THE Assessment_Service SHALL replace the Confirmed_Assessment, attribute it to that Physician, and increase Assessment_Version by exactly 1.
8. WHEN the assigned Physician successfully clears a Confirmed_Assessment, THE Assessment_Service SHALL remove the Confirmed_Assessment, blank the Editable_Assessment, increase Editable_Assessment_Revision by exactly 1, and increase Assessment_Version by exactly 1 while permitting a later edit and reconfirmation from that unconfirmed version.
9. IF an update or clear operation is requested before a Confirmed_Assessment exists, THEN THE Assessment_Service SHALL reject the operation with a state-conflict error.
10. IF a caller is not the assigned Physician for the Consultation, THEN THE Assessment_Service SHALL return a not-found response for Assessment editing, confirmation, update, and clearing without including clinical data in the response or operational logs.
11. IF a Consultation is outside Post_Consult_State, THEN THE Assessment_Service SHALL reject Confirmed_Assessment confirmation, update, and clearing with a state-conflict error.
12. IF an Assessment write supplies an expected Assessment_Version, Editable_Assessment_Revision, Gate_Revision, assignment revision, or applicable canonical digest different from current authoritative state, THEN THE Assessment_Service SHALL reject the write with the corresponding deterministic stale-state error.
13. WHEN an Assessment write is an Idempotent_Replay after authentication and assignment authorization succeed, THE Assessment_Service SHALL return the original actor-scoped response without changing Editable_Assessment, Confirmed_Assessment, Assessment_Version, Gate_Token state, or Dependent_Artifact state again.
14. IF an Assessment write repeats an Idempotency_Key within the same operation, Consultation, and actor scope with a different canonical payload, THEN THE Assessment_Service SHALL reject the write with an idempotency-conflict error.
15. IF an Assessment write fails before a new Assessment state commits, THEN THE Assessment_Service SHALL preserve the pre-write Editable_Assessment, Confirmed_Assessment, and Assessment_Version while preserving any fail-closed Gate_Token family revocation and generation lock that completed before the failure.
16. WHEN confirmation succeeds, THE Assessment_Service SHALL atomically create Token_Family_Epoch 1 for the new Assessment version in an unrevoked state, persist history/idempotency/audit intent, and leave generation unavailable solely because no Gate_Token has yet been issued; confirmation SHALL NOT create an uncleared `assessment_change` lock.
17. WHEN authoritative assignment changes, THE assignment writer SHALL atomically increment assignment revision, increment Gate_Revision, set `reassignment`, revoke the current Token_Family_Epoch, and prevent token issuance, generation, finalization, and release under the prior assignment.
18. WHILE the Confirmed_Assessment Physician differs from the currently assigned Physician, THE Assessment_Gating_System SHALL reject protected actions until the new assigned Physician explicitly updates or re-attests the Assessment through the versioned Assessment-change protocol, or clears it.
19. WHEN the new assigned Physician successfully updates, re-attests, or clears the Assessment after reassignment, THE transition SHALL increment Assessment_Version, attribute the action to the new Physician, create Token_Family_Epoch 1 for the new version, and clear only the matching `reassignment` and `assessment_change` reasons.
20. THE canonical session and assignment writer SHALL update the primary Session item, consultation-scoped Session projection, monotonic session/assignment revisions, and consultation safety fences in one transaction; authorization SHALL use a strongly consistent point read of that projection rather than a GSI or unconstrained Query.

### Requirement 3: Diagnosis Candidate Presentation

**User Story:** As a Physician, I want an unbiased diagnosis picker and manual entry option, so that I can record an independent Assessment without exposed AI ranking mechanics.

#### Acceptance Criteria

1. WHEN the assigned Physician requests diagnosis candidates, THE Candidate_Service SHALL use an idempotent candidate-evaluation write to evaluate safety and create an immutable Candidate_Evaluation snapshot before any side-effect-free search or scrolling request can return candidates.
2. THE Candidate_Service SHALL support bounded diagnosis-name search, diagnosis-name scrolling, an idempotent candidate-selection write, and a separate manual Editable_Assessment write; candidate selection SHALL include the committed evaluation identifier, exact candidate name, expected Editable_Assessment_Revision, and current snapshot revisions.
3. WHILE the Physician has not selected or manually entered a diagnosis, THE Candidate_Service SHALL keep the Editable_Assessment blank.
4. WHEN the Physician selects a candidate through the dedicated selection operation or manually enters a diagnosis, THE Assessment_Service SHALL increase Editable_Assessment_Revision, make the Editable_Assessment non-blank, record the authoritative source, and avoid creating a Confirmed_Assessment.
5. WHEN the Red_Flag_Router returns `ROUTINE`, THE Candidate_Service SHALL return candidate items that contain a diagnosis name and no other candidate field.
6. WHEN the Red_Flag_Router returns `WARNING`, THE Candidate_Service SHALL return diagnosis-name-only candidates together with separate safety-routing metadata.
7. WHEN the Red_Flag_Router returns `EVALUATION_FAILED`, THE Candidate_Service SHALL return `RED_FLAG_EVALUATION_FAILED` without candidate data, cached candidate data, or a prior Candidate_Evaluation snapshot.
8. THE Candidate_Service SHALL exclude confidence scores, percentages, solver identifiers, rank values, ICD codes, AI-attribution wording, and Protected_Output content from every Physician-visible candidate item and pre-confirmation response.
9. IF the Red_Flag_Router returns `REFER_F2F` or `EMERGENCY`, THEN THE Candidate_Service SHALL suppress routine Diagnosis_Candidates and return only the Red_Flag_Outcome, applicable rule identifiers, and safety-routing metadata.
10. WHEN the same Normalized_Clinical_Input, Clinical_Input_Revision, Ruleset_Version, Catalog_Version, and Policy_Activation_Revision are evaluated repeatedly, THE Candidate_Service SHALL return the same ordered Diagnosis_Candidate names using deterministic rules and tie-breakers without invoking the AI_Inference_Service.
11. WHEN the Physician manually enters a diagnosis, THE Assessment_Service SHALL permit confirmation without requiring selection of a Diagnosis_Candidate.
12. BEFORE every candidate search, scroll, page, display, or selection response, THE Candidate_Service SHALL compare the snapshot's Clinical_Input_Revision, normalized-input digest, Ruleset_Version, Catalog_Version, and Policy_Activation_Revision with current authoritative state; any mismatch SHALL return `STALE_CANDIDATE_EVALUATION` without candidate or prior routing payload and require a new Candidate_Evaluation.
13. EVERY candidate cursor SHALL be opaque, integrity protected, and bound to Consultation, evaluation identifier, snapshot revisions, normalized search filter, and page size; cursor reuse outside that scope SHALL be rejected without candidate data.
14. THE Candidate_Service SHALL expose candidates only from a snapshot whose metadata status is `committed`; chunks written under a `building` snapshot SHALL remain unreachable by read, search, scroll, display, and selection operations.
15. IF all bounded candidate chunks cannot fit the approved transaction budget, THE Candidate_Service SHALL conditionally write immutable chunks under a build identifier, verify their count and aggregate digest, and atomically commit snapshot metadata, routing/lock transition, idempotency response, and audit intent; abandoned builds SHALL expire without becoming visible.
16. WHEN candidate selection is requested, THE Candidate_Service SHALL verify the evaluation is committed and fresh, the selected diagnosis exactly belongs to its immutable chunk set, and the expected Editable_Assessment_Revision still matches before recording source type `candidate_selection`.
17. Candidate search SHALL use a bounded normalized-prefix directory or another documented no-scan structure within the committed snapshot and SHALL enforce configured read-count and byte limits rather than filtering an unbounded set of chunks.
18. WHEN the assigned Physician focuses or selects an exact Diagnosis_Candidate in a committed fresh Candidate_Evaluation, THE Candidate_Service SHALL expose a side-effect-free candidate-scoped CPG_Preview through a separate response shape; the Diagnosis_Candidate item itself SHALL remain diagnosis-name-only.
19. THE CPG_Preview SHALL contain at most three structured patient facts supporting why the candidate was offered, at most three missing or discriminating confirmation questions, one approved source reference containing title, publisher, year or effective date, and review status, and an explicit instruction that the Physician must independently select or enter and confirm the Assessment.
20. THE CPG_Preview SHALL NOT contain confidence, score, rank, verdict, hidden-chain reasoning, solver/model identity, ICD code, treatment, medication option, dosage, full clinical template, or any Protected_Output content, and its construction SHALL make zero AI_Inference_Service and zero generation-fallback calls.
21. THE Candidate_Service SHALL construct CPG_Preview content only from the committed evaluation snapshot, Normalized_Clinical_Input, and immutable preview-eligible catalog/source metadata selected by the current Policy_Activation_Revision; missing, unpublished, deprecated, unreviewed, incompatible, or unverifiable metadata SHALL return `CPG_PREVIEW_UNAVAILABLE` without a prior or partial preview.
22. BEFORE every CPG_Preview response, THE Candidate_Service SHALL authenticate and authorize current assignment, verify exact candidate membership, require the same evaluation freshness dimensions as candidate display, require a candidate-permitting current Red_Flag_Outcome, and return `Cache-Control: no-store`; mismatch or suppression SHALL return the applicable stale or routing error without preview data.

### Requirement 4: Deterministic Red-Flag Routing

**User Story:** As a Physician, I want deterministic safety routing before diagnosis selection and protected generation, so that urgent cases cannot continue through the routine CDS path.

#### Acceptance Criteria

1. WHEN a Candidate_Evaluation is requested, THE Red_Flag_Router SHALL evaluate the current Normalized_Clinical_Input before the Candidate_Service returns candidate data.
2. WHEN Gate_Token issuance is requested, THE Gate_Token_Service SHALL require a normalized Clinical_Input_Head whose normalization-complete fence equals the current Clinical_Input_Source_Fence, capture one authoritative Clinical_Input_Snapshot, and execute and durably persist a fresh `protected_generation` red-flag evaluation before deciding token eligibility.
3. WHEN any Protected_Output generation is requested with a Gate_Token, THE Red_Flag_Router SHALL capture and reevaluate the current Clinical_Input_Snapshot immediately before inference or fallback generation and reject if the Clinical_Input_Head is dirty or its source fence differs from the token.
4. THE Clinical_Input_Head SHALL assign a new Clinical_Input_Revision through conditional compare-and-swap whenever the canonical source vector, source-membership version, canonicalization version, or normalized digest changes; concurrent equivalent normalization SHALL converge on one revision.
5. THE Red_Flag_Router SHALL bind every evaluation to Clinical_Input_Revision, Clinical_Input_Source_Fence, source-membership version, normalized-input digest, Ruleset_Version, Policy_Activation_Revision, evaluation stage, and a unique evaluation identifier.
6. WHEN the same Normalized_Clinical_Input and immutable policy bundle are evaluated, THE Red_Flag_Router SHALL return the same Red_Flag_Outcome and sorted rule identifiers.
7. IF red-flag normalization, snapshot capture, schema validation, policy loading, or evaluation cannot complete, THEN THE Red_Flag_Router SHALL return `EVALUATION_FAILED` and fail closed before candidate display, token issuance, or Protected_Output generation.
8. IF an `EVALUATION_FAILED` outcome is detected after Protected_Output processing starts, THEN THE Protected_Generation_Service SHALL stop processing before any further inference, fallback, publication, or current-output persistence.
9. WHEN a completed red-flag evaluation matches multiple severities, THE Red_Flag_Router SHALL apply the fixed precedence `EMERGENCY`, `REFER_F2F`, `WARNING`, then `ROUTINE`.
10. WHEN a completed red-flag evaluation matches no configured red-flag rule, THE Red_Flag_Router SHALL return `ROUTINE`.
11. IF the Red_Flag_Router returns `WARNING`, `REFER_F2F`, `EMERGENCY`, or `EVALUATION_FAILED`, THEN token issuance and generation of all seven Protected_Output types SHALL be rejected.
12. WHEN the Red_Flag_Router returns `WARNING`, THE Candidate_Service SHALL return diagnosis-name-only candidates with prominent, separately structured safety-routing metadata.
13. IF the Red_Flag_Router returns `REFER_F2F` or `EMERGENCY`, THEN THE Candidate_Service SHALL suppress routine Diagnosis_Candidates.
14. WHEN a clinical non-routine evaluation is produced, THE Assessment_Gating_System SHALL atomically persist the current evaluation, set or update the bounded clinical-safety episode, set `red_flag` and `acknowledgment_pending`, increment Gate_Revision, and permanently revoke the current Token_Family_Epoch before returning a response.
15. WHEN `EVALUATION_FAILED` is produced, THE Assessment_Gating_System SHALL atomically persist the failed evaluation, set `evaluation_failed`, increment Gate_Revision, and permanently revoke the current Token_Family_Epoch before returning a response; persistence failure SHALL still fail closed.
16. WHILE a clinical non-routine or failed outcome is current, THE applicable generation lock SHALL survive retries, reconnections, and service restarts.
17. WHEN a fresh successful evaluation replaces the immediately preceding `EVALUATION_FAILED` for the same current Clinical_Input_Revision, Clinical_Input_Source_Fence, and Policy_Activation_Revision, THE Assessment_Gating_System SHALL conditionally clear only `evaluation_failed`, increment Gate_Revision, and preserve every unrelated lock; operational evaluation failure does not require Physician acknowledgment.
18. WHEN a fresh deterministic evaluation changes a prior `WARNING`, `REFER_F2F`, or `EMERGENCY` outcome to `ROUTINE`, THE Assessment_Gating_System SHALL retain `red_flag` and `acknowledgment_pending` until the assigned Physician acknowledges the current bounded clinical-safety episode.
19. WHEN the assigned Physician acknowledges the current clinical-safety episode, THE acknowledgment SHALL include the episode identifier and expected Gate_Revision, and THE Assessment_Gating_System SHALL conditionally clear only matching `red_flag` and `acknowledgment_pending` reasons after verifying the latest generation-stage evaluation is `ROUTINE` for the current Clinical_Input_Revision, Clinical_Input_Source_Fence, and Policy_Activation_Revision; if no unrelated blocking lock remains, the same transaction SHALL increment Token_Family_Epoch and create a new unrevoked family without modifying any revoked epoch.
20. A fresh `ROUTINE` evaluation performed for token issuance SHALL conditionally clear only recoverable `evaluation_failed` and `clinical_input_changed` locks that match the current head, increment Gate_Revision when lock state changes, and preserve `assessment_change`, `reassignment`, clinical red-flag, acknowledgment, operator, and recovery locks; if no blocking lock remains and the current epoch is revoked, the same transaction SHALL increment Token_Family_Epoch and create a new unrevoked family before token signing.
21. A repeated equivalent `ROUTINE` generation evaluation with unchanged Clinical_Input_Revision, Clinical_Input_Source_Fence, Policy_Activation_Revision, outcome, Token_Family_Epoch, and lock state SHALL NOT increment Gate_Revision or invalidate an otherwise current Gate_Token merely because a new evaluation identifier or timestamp was recorded.
22. THE Assessment_Gating_System SHALL define one owner and clear precondition for every lock reason, including `clinical_input_changed` and `reassignment`; no acknowledgment, evaluation, retry, assignment change, or operator command SHALL clear an unrelated lock reason.
23. EVERY mutation of an authoritative clinical-input source SHALL use one bounded transaction to conditionally update that source and its source revision, increment Clinical_Input_Source_Fence and Gate_Revision, mark the Clinical_Input_Head dirty, set `clinical_input_changed`, permanently revoke the current Token_Family_Epoch when present, and write idempotency/audit intent.
24. AN authoritative source that cannot participate in the consultation safety transaction SHALL NOT be read directly for gate authorization; trusted ingestion SHALL first materialize an immutable versioned `app_core` projection and atomically advance the Clinical_Input_Head before that source becomes eligible.
25. WHEN an authoritative source changes, every Gate_Token, job, candidate snapshot, and current artifact bound to an earlier Clinical_Input_Source_Fence SHALL become immediately invalid or effectively stale without waiting for normalization, routing, or background denormalization.
26. Repeated equivalent non-routine evaluations for the same Clinical_Input_Source_Fence, Policy_Activation_Revision, outcome, and sorted rule identifiers SHALL map to one bounded clinical-safety episode and SHALL NOT continually move the acknowledgment target or increment Gate_Revision; a materially different or more severe result SHALL create or supersede the episode according to documented severity and stage rules.
27. A revoked Token_Family_Epoch SHALL be immutable and SHALL never be unrevoked; all recovery paths that restore eligibility SHALL create the next epoch conditionally and preserve prior epoch history.

### Requirement 5: Signed Gate-Token Issuance and Revocation

**User Story:** As a platform security owner, I want signed and version-bound Gate_Tokens, so that protected generation can prove a current Physician-confirmed Assessment exists.

#### Acceptance Criteria

1. WHEN Gate_Token issuance is requested for an assigned Physician with a current Confirmed_Assessment in Post_Consult_State, THE Gate_Token_Service SHALL capture a revision-fenced Clinical_Input_Snapshot, run and persist a fresh `protected_generation` evaluation, apply the lock transitions in Requirement 4, and issue only when the result is `ROUTINE` and no blocking lock or acknowledgment remains.
2. THE Gate_Token_Service SHALL bind each Gate_Token to issuer, audience, `consultationId`, `assessmentVersion`, `tokenFamilyEpoch`, `physicianActorId`, assignment revision, `clinicalInputRevision`, `clinicalInputSourceFence`, `gateRevision`, `rulesetVersion`, `policyActivationRevision`, the applicable immutable generation-component versions, a unique token identifier, issuance time, and expiration time.
3. THE Gate_Token_Service SHALL return the Gate_Token only after authenticating and authorizing the assigned Physician and conditionally persisting token state against the same current Assessment_Version, Token_Family_Epoch, assignment revision, Clinical_Input_Revision, Clinical_Input_Source_Fence, Gate_Revision, Ruleset_Version, Policy_Activation_Revision, and unrevoked family.
4. THE Gate_Token_Service SHALL sign tokens with an allow-listed asymmetric `ES256` key held in a per-environment AWS KMS `ECC_NIST_P256` signing key, SHALL place an opaque rotation `kid` in the protected JOSE header, and SHALL use a reviewed standards-compliant adapter for KMS DER ECDSA to JWS `R || S` encoding rather than implementing cryptographic primitives.
5. THE Gate_Token_Service SHALL enforce issuer and audience validation, a maximum token lifetime of 5 minutes, and a maximum clock-skew allowance of 30 seconds using an injected clock for deterministic tests.
6. THE Gate_Token_Service SHALL set `Cache-Control: no-store` on token responses and SHALL accept Gate_Tokens only in the approved JSON request field or approved authorization header, never in URLs, query strings, cookies, logs, or error details.
7. THE Gate_Token_Service SHALL NOT persist plaintext Gate_Tokens in domain token records; an idempotency record MAY retain the original compact token only as envelope-encrypted ciphertext under a dedicated environment key, scoped to operation, Consultation, and actor, with decrypt permission limited to token replay and TTL no later than token expiration plus clock skew.
8. WHEN a Gate_Token is verified, THE Gate_Token_Service SHALL allow-list the algorithm and validate signature, `kid`, issuer, audience, expiration, unique token identifier, exact Token_Family_Epoch and revocation state, Consultation identifier, Assessment_Version, Physician identifier and confirmation ownership, assignment revision, Clinical_Input_Revision, Clinical_Input_Source_Fence, Gate_Revision, Ruleset_Version, Policy_Activation_Revision, and applicable generation-component versions against authoritative current server state.
